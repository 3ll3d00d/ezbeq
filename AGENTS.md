# ezbeq — Agent Guide

## Project Overview

**ezbeq** is a full-stack web application that provides a browser and management interface for [BEQ (Bass EQ) filters](https://beqcatalogue.readthedocs.io/). It loads BEQ filters into audio DSP devices and supports:

- **MiniDSP** devices (2x4HD, 4x10, 10x10, DDRC-24, DDRC-88, HTx, SHD, 8x12CDSP, and others via [minidsp-rs](https://github.com/mrene/minidsp-rs))
- **Monolith HTP-1** (Atmos processor)
- **JRiver Media Center**
- **Q-Sys** (via QRC protocol)
- **CamillaDSP**

This repo has two distinct sub-projects with their own conventions:
- **Backend** (Python): see `ezbeq/AGENTS.md`
- **Frontend** (React): see `ui/AGENTS.md`

## Architecture

```
ezbeq/           # Python backend package
  apis/          # Flask-RESTx REST endpoints
  *.py           # Device integrations and core modules
  ui/            # Built React frontend (served statically)
ui/              # React source code
  src/
    components/
    services/
tests/           # Pytest test suite
docs/            # MkDocs documentation
examples/        # Device configuration YAML examples
docker/          # Dockerfile, compose files, helper scripts for containerised deployment
```

**Server architecture:** Flask (REST API at `/api`) + Twisted (static frontend + WebSocket) hybrid. The built React app (`ezbeq/ui/`) is served by a raw `twisted.web.static.File`-based resource tree (`ReactApp`/`PrecompressedFile` in `main.py`), **not** through Flask — `flask_compress` only ever applies to `/api` responses, never to the JS/CSS bundle. Static assets are pre-compressed to `.gz`/`.br` at build time (see `compression` plugin in `ui/vite.config.js`) and served with long-lived immutable caching; `index.html` is always revalidated since it references the current content-hashed asset filenames.

## Key Modules

| Module | Purpose |
|--------|---------|
| `ezbeq/main.py` | Flask app factory + Twisted server setup |
| `ezbeq/config.py` | Config loading from `~/.ezbeq/ezbeq.yml` |
| `ezbeq/catalogue.py` | BEQ catalogue management (HTTP caching, SQLite) |
| `ezbeq/device.py` | Abstract base classes: `Device`, `DeviceState`, `SlotState` |
| `ezbeq/minidsp.py` | MiniDSP integration (PEQ routing, biquad allocation, minidsp-rs WebSocket) |
| `ezbeq/camilladsp.py` | CamillaDSP integration (filter pipeline management) |
| `ezbeq/htp1.py` | Monolith HTP-1 integration |
| `ezbeq/jriver.py` | JRiver Media Center integration (MCWS API) |
| `ezbeq/qsys.py` | Q-Sys integration (QRC protocol) |
| `ezbeq/iir.py` | IIR/biquad filter utility functions |
| `ezbeq/apis/devices.py` | Device state/control API (v1, v2, v3 endpoints) |
| `ezbeq/apis/ws.py` | WebSocket server for real-time device updates |

## Configuration

The app reads from `~/.ezbeq/ezbeq.yml`. Example configs for all supported devices are in the `examples/` directory.

## API Documentation

Swagger UI is auto-generated by Flask-RESTx and available at `http://localhost:8080/api/` when running locally.

## Deployment

- **Standalone executable:** Built via `ezbeq.spec` (PyInstaller)
- **Systemd service:** Example in README for Raspberry Pi / Linux
- **ReadTheDocs:** Documentation hosted at https://ezbeq.readthedocs.io/

## Release Management

- The `version` field in `pyproject.toml` is managed by the maintainer when cutting releases. Agents must never modify it, including as an incidental side effect of unrelated changes — leave it untouched even if it appears to be out of sync with recent commits.

## CI/CD

GitHub Actions workflows:
- `test.yaml` ("run tests") — Pytest, path-filtered to `ezbeq/**`, `tests/**`, `pyproject.toml`, `uv.lock`
- `test-ui.yaml` ("run ui tests") — Vitest, path-filtered to `ui/**`
- `test-mobile.yaml` ("run mobile tests") — Jest + typecheck, path-filtered to `mobile/**`
- `create-app.yaml` — Builds and publishes the application (PyPI, PyInstaller, mobile). Also dispatches to the separate `3ll3d00d/ezbeq-docker` repo on every PyPI release, which publishes `ghcr.io/3ll3d00d/ezbeq-docker`.
- `docker.yaml` — Builds `docker/Dockerfile` from local source (no PyPI dependency) and publishes `ghcr.io/3ll3d00d/ezbeq` on push to `main`/`dev` and on version tags. Independent of `create-app.yaml` and of the legacy `ezbeq-docker` repo/image — both keep publishing in parallel.
- `claude.yml` — AI assistant integration (triggered by `@claude` comments)
- `claude-code-review.yml` — Automated code review on PRs

Each test workflow only *triggers* when its own subtree changes — editing `ui/` alone will not run
`mobile/` tests even if the change breaks a mobile component that mirrors it. Commits normally land
directly on `main` (no required PR review), and branch protection does not block a red run from
merging — pushes to `main` with a failing check go through with a "Bypassed rule violations"
notice rather than being rejected. In practice this means **CI is a report, not a gate**: nothing
stops a broken commit from landing or staying broken until a human happens to check Actions. See
"Before pushing" below.

## Before pushing

Because CI here doesn't block a bad push (see above), treat every push to `main` as if it were
about to merge unreviewed — the test run you do locally beforehand is the only real gate.

1. **Run the full test suite for every sub-project you touched — not just the files you edited.**
   `pytest` / `yarn test:unit` / `npm test` each run their whole suite in seconds to low minutes;
   narrowing to "the tests near my change" is exactly how an unrelated pre-existing failure (or one
   your change silently caused elsewhere in the same suite) goes unnoticed. Include the typecheck
   step too where one exists (`npm run typecheck` in `mobile/`).
2. **If the change touches logic that's deliberately mirrored across sub-projects** — `mobile/`
   is a port of `ui/src/components/main/` (see `mobile/AGENTS.md`) — run both suites, even if the
   diff only touches one side. CI's path filters won't do this for you.
3. **Never push knowing a test is red**, including one you've diagnosed as "pre-existing and
   unrelated to my change." Either fix it in the same push or stop and tell the user before
   pushing — don't rely on them to notice the Actions tab later. A failure that's pre-existing today
   is exactly the kind that silently sits on `main` for days otherwise (see git history around
   commit `f8c49c4` for a real example: it shipped a mobile CI failure that went unnoticed for two
   days).
4. **After pushing, confirm the pushed commit's CI actually went green** — `gh run list --branch
   main --limit 5` (match the commit by title/SHA) or `gh run watch <run-id>`. A push isn't done
   until you've seen the run succeed, not just until `git push` returns.
